
## 1. Обязательный стек технологий

Все технологии обязательны. 
| Технология | Требование |
|---|---|
| **React 18 + TypeScript** | Основа приложения. Только функциональные компоненты |
| **TanStack Router** | Клиентская маршрутизация.
| **Стейт-менеджер** | На выбор студента: Zustand, Jotai или Redux Toolkit. Выбор **обосновать на защите** |
| **Дизайн-система** | На выбор студента |
| **CSS Modules** | Вся стилизация компонентов. Глобальные стили — только для переменных и сброса |
| **Fetch API или XHR** | Все HTTP-запросы |

## 2. Требования к проекту

### 2.1 Предметная область и задача

- Приложение должно решать **реальную, конкретную задачу** пользователя. Абстрактные «todo-листы» и «списки продуктов» не принимаются.
- Предметную область согласовать **до начала разработки**.
- На защите необходимо чётко сформулировать: **кто пользователь, какую проблему решает приложение и почему существующие решения не устраивают**.

### 2.2 Работа с API

- Обязательна интеграция с **внешним или собственным REST API**. Допустимые варианты: публичный API, самостоятельно написанный бэкенд.
- Реализовать : создание, чтение, обновление, удаление данных.
- Обязательно: **обработка состояний загрузки и ошибок** на уровне UI. Пустые экраны без индикации недопустимы.
- Все ответы API типизированы — для каждого ресурса определены TypeScript-интерфейсы или типы.

### 2.3 Архитектура

- Применить слоистую архитектуру с чётким разделением ответственности между слоями. Выбор обосновать на защите.
- Вся логика работы с API вынесена в отдельный слой (сервисы / api-клиент). Компоненты не вызывают `fetch` напрямую.

- Не менее **трёх маршрутов** с осмысленной навигацией.

---

## 3. Требования к качеству кода

- Строгая типизация: `"strict": true` в `tsconfig.json`. Использование `any` не допускается без комментария-обоснования.
- Переиспользуемые компоненты вынесены отдельно и не содержат бизнес-логики.
- Кастомные хуки для инкапсуляции логики (например: `useAuth`, `useFilters`, `usePagination`).
- Настроены **ESLint + Prettier**. Код должен проходить линтер без ошибок.
- `README.md` с описанием проекта, инструкцией запуска и структурой папок.

## 4. Защита проекта

Защита состоит из двух частей: **демонстрация** работающего приложения и **техническое интервью** по принятым решениям.

### Обязательные вопросы на защите

1. Почему выбран именно этот стейт-менеджер? Чем он отличается от альтернатив в контексте вашей задачи?
2. Как организована работа с API? Как обрабатываются ошибки сети? Как реализована отмена запросов (если есть)?
3. Объясните структуру папок. Почему именно так? Какие правила разделения ответственности применялись?
4. Как работает маршрутизация? Как реализована защита маршрутов? Как передаются параметры?
5. Какие проблемы возникли в процессе разработки? Как были решены?

> **Важно:** незнание принятых технических решений, даже при работающем коде, является основанием для снижения оценки.
